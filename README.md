## 一、赛题背景：这不是一个 Demo 题

### 1.1 比赛与任务

来自**行业智能体创新挑战赛**的赛题四。与常见的"跑个模型看指标"不同，这道题要求的是一个**能交付给行业使用的完整系统**：

- **输入**：城市桥梁与轨道结构的现场/航拍巡检影像
- **输出**：可入库的**七字段结构化记录**
- **交付**：代码 + 方案设计书 + 预测结果，按赛事规定目录结构打包

### 1.2 七字段业务合同

| 字段 | 含义 | 轨道记录 | 桥梁记录 |
|---|---|:---:|:---:|
| `questionCategory` | 问题类型（桥梁 / 轨道） | ✅ | ✅ |
| `bridgeName` | 桥梁名称 | 空 | ✅ |
| `defectLocation` | 缺损位置 / 构件 | 空 | ✅ |
| `filename` | 照片编号 | ✅ | ✅ |
| `defectType` | 缺损类型 | ✅ | ✅ |
| `defectDescription` | 病害描述（性质/范围/程度） | 空 | ✅ |
| `ratingScale(1-5)` | 评定标度 | 空 | ✅ |

**关键点**：轨道和桥梁是**两套不同的表头**。轨道按既有作业习惯只落缺损类型，其余留空；桥梁要填全。系统必须按业务合同填报，不能把两张表混成一张"什么都写"的通表。

### 1.3 评分规则决定了难度

> **除 `filename` 外，其余字段全部需要匹配，匹配正确才得分。**

这条规则的含义是：**"能跑通"和"能得分"是两件事**。模型必须写对桥梁名、判对缺损类型、描述贴合原意、标度落在正确档位——任何一项错，这条记录就不算分。

## 三、任务难在哪：三个必须正面解决的矛盾

| 挑战 | 真实数据 | 为什么不能硬扛 |
|---|---|---|
| **病害类别长尾** | 48 种病例标签中，**26 种仅有 1 例**样本 | 直接全量微调会严重过拟合，且训练成本不可控 |
| **全量大模型成本高** | 330 张全走 27B，模型加载与推理时间不可接受 | 巡检是高频任务，算力必须按需分配 |
| **记录必须可复查** | 巡检台账要能回溯到原图与构件 | 只给一条结论、丢掉了原图身份，等于不可用 |

## 四、技术方案与三个创新点

### 4.1 主链路

```
输入图片
   ↓
2B 提取视觉特征（全量识别，330 张全覆盖）
   ↓
轨道 / 桥梁 任务识别
   ↓
多信号风险门控（三级风险筛选）
   ├── 无需复核 → 保留 2B 初判 → 统一规则校验后输出
   └── 触发复核 → 27B 独立看图提出建议 → 检查通过才允许更新
```

### 4.2 创新点一：多信号风险门控，而不是单一置信度阈值

常见做法是"置信度低于 0.8 就送大模型"。本项目用的是**两类信号 + 三级筛选**：

| 风险来源 | 触发条件 | 解决什么 |
|---|---|---|
| **模型判断犹豫** | 多个类别分数接近，或接近"有无病害"边界 | 抓"拿不准"的样本 |
| **缺少训练支持** | 与已标注样本差异较大（分布外） | 抓"没见过"的样本 |
| **补充规则** | 高置信但参考严重不足时也可触发 | 防止"自信地错" |

> 只用置信度会漏掉第二类——模型可能很自信，但它压根没见过这类病害。

### 4.3 创新点二：冻结基座 + 轻量分类头，正面处理长尾

面对 26/48 类只有 1 例样本的现实，**不做全量微调**：

| 项 | 做法 |
|---|---|
| 基座 | **冻结** 2B，只提取图像特征 |
| 分类头 | 逻辑回归（轨道 22 类 / 桥梁有无病害两分类） |
| 训练数据 | 轨道 **800 条** / 桥梁 **2602 条** |
| 病例库 | **698 条 / 48 种**已有标签，用于检索参考 |

好处：训练成本低、可快速迭代、在长尾分布下比全量微调更稳。

### 4.4 创新点三：27B 不是最终裁判，而是受控复核者

| 情形 | 处理 |
|---|---|
| 门控未触发 | 保留 2B 初判，统一规则校验后输出 |
| 复核完成 | 27B 独立看图提建议，**检查通过才允许更新** |
| 复核异常（缺模型 / 超时 / 非法输出） | **保留有效 2B 初判** |

> 这条设计的含义：宁可承认能力降级，也不静默换模型糊过去。大模型在这里是"第二双眼睛"，不是"最终裁决"。

## 五、真实运行证据

| 指标 | 结果 |
|---|---|
| 全量识别 | **330 / 330 完成**（每张均有实时视觉计算） |
| 按需复核 | **4 / 4 完成**（桥梁 3 张 / 轨道 1 张） |
| 线上入口计时 | 约 **156 秒**（同次完整进程约 170 秒） |

> 两次真实运行均为 330 张，非严格同环境消融。

**算力效率**：330 张里只有 4 张走了 27B，**复核率约 1.2%**——这就是"按需协同"的实际收益。

## 六、工程落地性

| 落地要点 | 具体做法 |
|---|---|
| **业务合同驱动** | 桥梁 / 轨道两套字段规则，按 `questionCategory` 分流填报 |

| **可审计** | 每次运行落 manifest 与 evidence，SHA256 可核 |

## 八、关键设计补充

### 8.1 门控阈值不是拍脑袋

风控门的阈值来自扫描实验，`reports/gate_threshold_study.json` 记录了阈值选择过程与依据。

### 8.2 可复现性

- `REPRODUCIBILITY.md`：环境、配置、校验流程
- 所有 manifest 记录 SHA256，支持逐项核对
- 运行入口不改模型、不改门控、不改验收规则
